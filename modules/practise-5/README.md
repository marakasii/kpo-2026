# Практика 5. Порождающие паттерны GoF

## Цель

Научиться применять порождающие паттерны GoF — **Builder** и
**Factory Method** — на предметной области уведомлений.

## Контекст

Разрабатывается сервис уведомлений для интернет-магазина. Он должен создавать
уведомления нескольких видов:

| Вид | Особенность |
|---|---|
| Email | Нужен адрес получателя и тема письма. |
| Push | Нужен идентификатор устройства. |
| In-app | Нужен идентификатор пользователя. |

У каждого уведомления есть текст, время создания, приоритет и канал доставки.
Время передаётся явно: не используйте системные часы внутри модели.

## Часть 1. Builder для данных уведомления

Создайте Builder, который по шагам формирует черновик уведомления. Он должен
позволять указать канал, получателя, текст, время создания и приоритет.

Метод сборки возвращает неизменяемый черновик. Он обязан проверить следующие
правила:

- канал и получатель обязательны;
- текст не пустой и не состоит только из пробелов;
- приоритет находится в допустимом диапазоне, выбранном и описанном вами;
- время создания задано.

Пример ожидаемого использования в псевдокоде:

```text
draft = NotificationBuilder()
    .channel(EMAIL)
    .recipient("student@example.org")
    .text("Ваш заказ передан в доставку")
    .createdAt(2026-10-01 10:15)
    .priority(HIGH)
    .build()
```

## Часть 2. Абстрактная фабрика уведомлений

Преобразуйте черновик в настоящее уведомление с помощью абстрактной фабрики.

Определите общий контракт (абстрактную фабрику) с операцией создания
уведомления из черновика. Создайте конкретные фабрики для email, push и in-app
каналов. Каждая фабрика **внутри себя** создаёт специализированный Builder,
передаёт ему поля черновика и вызывает его финальный метод сборки. Клиентский
код не должен вызывать специализированные Builder-ы напрямую.

Структура в псевдокоде:

```text
interface NotificationFactory:
    create(draft) -> Notification

EmailNotificationFactory.create(draft):
    return EmailNotificationBuilder()
        .recipient(draft.recipient)
        .text(draft.text)
        .createdAt(draft.createdAt)
        .priority(draft.priority)
        .subject("Уведомление магазина")
        .build()
```

Каждая конкретная фабрика возвращает объект своего вида и переносит общие поля
из черновика, добавляя специфичное поле:

- email-фабрика создаёт email-уведомление с адресом и темой;
- push-фабрика создаёт push-уведомление с идентификатором устройства;
- in-app фабрика создаёт уведомление с идентификатором пользователя.

Точка сборки приложения сопоставляет канал черновика с конкретной фабрикой.
Клиентский код работает с абстрактной фабрикой и общим контрактом уведомления;
он не должен создавать конкретные уведомления, выбирать Builder или проверять
тип уведомления условными операторами.

Если позднее появится, например, SMS-канал, добавьте новый тип уведомления,
специализированный Builder и новую фабрику. Черновик и клиентский код изменять
не требуется.

## Тесты

Напишите тесты, принятые в выбранной экосистеме. Имена сценариев и отображаемые
названия тестов должны быть понятными и написанными по-русски.

1. Builder формирует черновик со всеми переданными полями.
2. Builder отклоняет пустой текст, отсутствующего получателя и недопустимый
   приоритет.
3. Каждая фабрика создаёт через свой Builder уведомление ожидаемого вида и
   переносит общие поля из черновика.
4. Email-фабрика через свой Builder добавляет адрес и тему, push-фабрика —
   идентификатор устройства, а in-app фабрика — идентификатор пользователя.
5. Интеграционный сценарий создаёт черновик Builder, выбирает абстрактную
   фабрику по каналу и проверяет итоговое уведомление через общий контракт.

Все тесты должны запускаться одной командой выбранного инструмента и не
зависеть от системных часов, сети или внешних сервисов.

## Что сдавать

- Неизменяемую модель черновика и Builder для неё.
- Общий контракт уведомления и конкретные виды уведомлений.
- Контракт абстрактной фабрики и фабрики для всех поддержанных каналов.
- Unit и интеграционные тесты.

## Как устроена реализация на Java

Структура модуля повторяет предыдущие практики:

```text
practise-5/
├── build.gradle.kts
├── src/main/java/studying/
│   ├── Main.java                 # Пример запуска
│   ├── model/                    # Черновик, контракт и виды уведомлений
│   ├── builder/                  # Общий и специализированные Builder-ы
│   ├── factory/                  # Абстрактный создатель и три фабрики
│   ├── configuration/            # Сборка зависимостей через Spring DI
│   └── service/                  # Клиент фабрик
└── src/test/java/studying/
    ├── builder/                  # Проверки сборки и валидации
    ├── factory/                  # Проверки видов и полей уведомлений
    └── service/                  # Mock-тесты и интеграция со Spring
```

### Builder: как собираются данные

`NotificationBuilder` хранит промежуточные значения. Каждый метод, например
`text(...)`, записывает одно поле и возвращает `this`, поэтому методы можно
вызывать цепочкой. `build()` создаёт `NotificationDraft`. Проверки выполняются
в конструкторе черновика, поэтому нельзя обойти их прямым вызовом `new`.

Черновик и готовые уведомления — Java `record`: их поля нельзя изменить после
создания. Изменение Builder после `build()` не изменяет предыдущий результат.

Приоритет — целое число: **1 — низкий, 2 — обычный, 3 — высокий**.
Если приоритет не указан, Builder использует 2. Все остальные общие поля
обязательны. Получатель и текст должны содержать непробельные символы.
Email также требует непустую тему. Время всегда передаётся явно.

### Factory Method: кто выбирает вид уведомления

`NotificationFactory` — абстрактный создатель с фабричным методом `create()`.
Наследники переопределяют этот метод: email-фабрика создаёт email, push-фабрика
создаёт push, in-app фабрика создаёт in-app уведомление. Каждая из них внутри
`create()` использует свой специализированный Builder.

Название «абстрактная фабрика» в задании обозначает общий контракт создателя.
Порождающий паттерн этой реализации — **Factory Method**: подклассы определяют
конкретный продукт, возвращаемый методом `create()`.

| Класс | Что нужно понять |
|---|---|
| `NotificationBuilder` | Пошагово собирает общий черновик. |
| `NotificationFactory` | Объявляет фабричный метод `create(draft)`. |
| `EmailNotificationFactory` | Переносит поля в `EmailNotificationBuilder` и добавляет тему. |
| `PushNotificationFactory` | Передаёт получателя в `PushNotificationBuilder` как `deviceId`. |
| `InAppNotificationFactory` | Передаёт получателя в `InAppNotificationBuilder` как `userId`. |
| `NotificationService` | Выбирает уже переданную фабрику и работает с `Notification`. |
| `ApplicationConfiguration` | Создаёт зависимости и сопоставляет каналы с фабриками. |

### DI: откуда сервис получает фабрики

Spring вызывает методы с `@Bean` в `ApplicationConfiguration`. Сначала
создаются фабрики, затем конфигурация передаёт их в конструктор
`NotificationService` в виде `Map<NotificationChannel, NotificationFactory>`.
Так выглядит внедрение зависимостей через конструктор.

Сервис находит фабрику по каналу и вызывает `create(draft)`. Он знает общие
контракты `NotificationFactory` и `Notification`. Конкретные классы продуктов
и специализированные Builder-ы выбираются внутри фабрик.

```text
NotificationBuilder.build()
        ↓
NotificationDraft
        ↓
NotificationService → фабрика из Map, переданной через DI
        ↓
NotificationFactory.create(draft)
        ↓
специализированный Builder.build()
        ↓
Notification
```

Тема email задаётся свойством Spring `notification.email.subject`.
По умолчанию она равна «Уведомление магазина». Фабрика получает тему через
конструктор и добавляет её ко всем создаваемым письмам.

Для SMS нужно добавить значение канала, новый вид уведомления, его Builder
и фабрику, затем зарегистрировать фабрику в `ApplicationConfiguration`.
Классы `NotificationDraft`, `NotificationBuilder` и `NotificationService`
при этом сохраняют свой код.

### Запуск из корня репозитория

```bash
# Checkstyle, тесты и проверка покрытия JaCoCo.
./gradlew :modules:practise-5:check

# Пример создания email-уведомления через Spring DI.
./gradlew :modules:practise-5:run
```

Отчёт тестов: `modules/practise-5/build/reports/tests/test/index.html`.
Отчёт покрытия: `modules/practise-5/build/reports/jacoco/test/html/index.html`.
`check` проверяет покрытие: не менее **90 % строк и 100 % ветвей**, как
в практике 4. Исключений классов из отчёта JaCoCo нет.

Checkstyle 14.1.0 проверяет основной код и тесты по стандартным Sun Checks
с теми же исключениями правил JavaDoc, что в практике 4. Правило имён методов
также разрешает кириллицу, чтобы сохранить русские имена сценариев из задания.
Любое нарушение стиля останавливает проверку. HTML-отчёты находятся в
`modules/practise-5/build/reports/checkstyle/main.html` и `test.html`.

Интеграционные тесты используют настоящие фабрики и Builder-ы для всех трёх
каналов. Уведомления создаются в памяти: отправка почты или обращение к сети
не требуются.

Для изучения кода удобно начать с `Main`, затем посмотреть `NotificationBuilder`,
`NotificationService`, `ApplicationConfiguration` и `EmailNotificationFactory`.
Во всех основных классах есть поясняющие комментарии на русском языке.
